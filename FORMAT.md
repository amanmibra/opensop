# The sopc format

This is the complete reference for writing sopc files, for people and for coding agents. If you are an agent asked to create or change voice-agent instructions in a sopc folder, read this whole file first, then follow the checklist at the end.

A full, commented example lives in [`examples/livekit-restaurant/sops/`](examples/livekit-restaurant/sops). JSON Schemas for every file are in [`spec/`](spec).

## The model in one paragraph

Each voice agent's prompt is assembled from three kinds of blocks. **Bases** are prompt text that isn't a procedure (identity, brand voice, context, policy). **SOPs** are procedures (goal, steps, forbidden actions, warning signs). **Agents** are one file per voice agent: which platform it runs on, which bases it inherits, values for placeholders, and text only it gets. Shared text is written once in a base or SOP and reaches many agents, either because the agent lists it (`inherits`) or because the block lists the agent (`agents`).

## Folder layout

```
<root>/                    any folder; a whole repo or e.g. sops/ inside one
  sopc.yaml              required; marks the root
  bases/<id>.md            prompt text, with optional YAML front matter
  procedures/<id>.md       SOPs in Markdown (recommended)
  procedures/<id>.yaml     or SOPs in YAML; both kinds can sit side by side
  agents/<id>.yaml         one per voice agent
  build/                   generated by `sopc`; never edit by hand
```

- **Ids are file names** without the extension: `bases/brand-voice.md` has id `brand-voice`. Use lowercase kebab-case.
- An id must be unique across bases and SOPs. An SOP is either `<id>.md` or `<id>.yaml`, not both.
- Files outside these folders are ignored.
- Every command works on `./sops` if `sops/sopc.yaml` exists, else on the current folder if `sopc.yaml` is there. Use `--dir` (or `-C`) for another folder, on any command: `sopc --dir path/to/sops`, `sopc validate --dir path/to/sops`.

## How a prompt is assembled

For each agent, in this order:

1. **Top bases.** First the agent's `inherits` list, in order, each preceded by its own parents. Then bases whose `agents` field targets this agent, alphabetically by id. Each base appears once.
2. **The agent's `instructions`.**
3. **SOPs** that target this agent, under `sops_heading`. SOPs in `sop_order` come first, then the rest alphabetically.
4. **Bottom bases** (`position: bottom`), with the same ordering rules.

Then every `{{name}}` placeholder is replaced: the agent's `variables` first, then `sopc.yaml` defaults. A placeholder with no value is a validation error.

## sopc.yaml

```yaml
version: 1                          # always 1
variables:                          # defaults for {{placeholders}}, for every agent
  staff_transfer: the manager on duty
sops_heading: "## Procedures"       # heading above the SOPs (this is the default)
sop_order: [allergen-check]         # SOPs placed first; the rest alphabetically
```

Every field is optional. An empty `sopc.yaml` is valid.

## bases/\<id\>.md

Markdown text, optionally preceded by YAML front matter between `---` lines. The text below the front matter is what goes into the prompt.

```markdown
---
agents: "*"            # optional: apply to every agent without them listing it
locked: true           # optional: agents can't exclude it
---
Speak warmly and briefly. Ask one question at a time.
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `inherits` | list of base ids | `[]` | Bases placed before this one wherever it's used. |
| `agents` | `"*"` or list | `[]` | Agents that get this base without inheriting it. `[]` means only agents that inherit it. |
| `exclude` | list | `[]` | Agents to leave out even if `agents` matches them. |
| `locked` | bool | `false` | No agent can exclude it. |
| `position` | `top` \| `bottom` | `top` | `bottom` goes after the SOPs, e.g. a call closing. |

A file with no front matter is valid: it's plain text that agents must inherit.

## procedures/\<id\>.md

An SOP is a procedure: a goal, when it applies, steps, things never to do, and warning signs. Write it in Markdown (recommended) or in YAML (next section). Both read into the same SOP and compile to the same prompt.

```markdown
---
agents: "*"
delivery: prompt
locked: true
---
# Allergen check

**Goal:** Customer leaves knowing whether their order is safe for their allergy.
**When:** Any order where the customer mentions a food allergy or dietary restriction.

Parents often ask on behalf of a child. Confirm who the allergy is for first.

## Steps
1. Ask if anyone in the order has a food allergy
2. Check each item against {{menu_allergen_link}} `tool: lookup_allergens` `required`

## Never
- Never say an item is "allergen-free" or "safe"
- Never place the order before allergens are confirmed `tool: place_order`

## Warning signs
- Customer mentions anaphylaxis or an EpiPen; transfer to {{staff_transfer}} `tool: transfer_to_staff`
```

| Part | Required | Written as | YAML field |
|---|---|---|---|
| Settings | no | Front matter between `---` lines, settings only: `agents`, `exclude`, `locked`, `delivery` (and `id`, which must match the file name). YAML comments here never reach a prompt. | same names |
| Name | **yes** | Exactly one `# ` heading, the first thing after the front matter. | `name` |
| Goal | no, but warned about | `**Goal:** text` | `description` |
| When | no | `**When:** text` | `scope` |
| Guidance | no | Any other paragraphs between the name and the first `##` section. Line breaks are kept. | `guidance` |
| Steps | **yes, at least one** | `## Steps`, then a numbered list | `procedureSteps` |
| Never | no | `## Never`, then a `-` list | `forbiddenActions` |
| Warning signs | no | `## Warning signs`, then a `-` list | `warningSigns` |

The rules are strict, so every SOP reads the same and mistakes are caught:

- Names are exact and case-sensitive: `**Goal:**`, `**When:**`, `## Steps`, `## Never`, `## Warning signs`. Anything else (`**Objective:**`, `## Notes`, `### Details`) is an error that lists the allowed names.
- A field continues on the following lines until a blank line; the lines are joined with a space.
- Under a section, only list items (`- ` or `1. `). An indented line continues the item above it. Blank lines are fine.
- Sections may come in any order; `sopc fmt` puts them in the order above.
- A list item can end with markers in backticks, in either order: `` `tool: lookup_allergens` `` (the tool's exact name, one word) and `` `required` `` (steps only: the tool call must happen). An item with markers is the YAML object `{text, tool, required}`; without, a plain string.
- Notes for people go in front-matter comments (`# ...`). Everything in the body is prompt text.

## procedures/\<id\>.yaml

The same SOP in YAML. `sopc convert` switches SOPs between the two formats.

```yaml
name: Allergen check
agents: "*"
delivery: prompt
description: Customer leaves knowing whether their order is safe for their allergy.
scope: Any order where the customer mentions a food allergy or dietary restriction.
guidance: |
  Parents often ask on behalf of a child. Confirm who the allergy is for first.
procedureSteps:
  - Ask if anyone in the order has a food allergy
  - text: Check each item against {{menu_allergen_link}}
    tool: lookup_allergens
    required: true
forbiddenActions:
  - Never say an item is "allergen-free" or "safe"
warningSigns:
  - text: Customer mentions anaphylaxis or an EpiPen; transfer to {{staff_transfer}}
    tool: transfer_to_staff
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `name` | string | required | Heading in the prompt. |
| `procedureSteps` | list of steps | required | Ordered steps; at least one. |
| `agents` | `"*"` or list | `[]` | Which agents get this SOP. `[]` means none. |
| `exclude` | list | `[]` | Agents to leave out even if `agents` matches them. |
| `locked` | bool | `false` | No agent can exclude it. |
| `delivery` | `prompt` \| `auto` \| `tool` | `prompt` | See below. |
| `description` | string | `""` | **The goal**: the outcome that means the SOP succeeded. Write it. |
| `scope` | string | `""` | When the SOP applies. |
| `guidance` | string | `""` | Free text that isn't a step, forbidden action or warning sign. |
| `forbiddenActions` | list of steps | `[]` | Things the agent must never do. |
| `warningSigns` | list of steps | `[]` | Situations needing special handling, usually escalation. |

**Colons.** YAML treats `: ` (colon then space) inside unquoted text as a key and value. Quote any step or field that contains one:

```yaml
forbiddenActions:
  - "Never say: we're fully booked"    # quoted: fine
  - Never say: we're fully booked      # unquoted: error colon_in_step
```

For long text, a `|` block avoids quoting entirely.

**YAML version.** Files are read as YAML 1.2. Unquoted `yes`, `no`, `on`, `off`, times like `1:30` and dates are plain text. Only bare numbers (`- 10`) and `true`/`false` are read as something other than text, so quote a step that is just a number or a boolean. Duplicate keys in one mapping are an error. Boolean fields (`locked`, `required`) take `true` or `false`; `yes`/`no` are accepted there too.

**Steps.** Each entry in `procedureSteps`, `forbiddenActions` and `warningSigns` is either a plain string or an object:

```yaml
- text: Check availability       # required
  tool: check_reservations       # optional: a tool the agent has
  required: true                 # optional, steps only: the tool call must happen
```

A step with a `tool` gets an instruction to use it ("Check availability. Use the `check_reservations` tool."), and the tool name is recorded in `build/lock.json`. Use the tool's exact name as the agent's code or platform defines it.

**Delivery.** Where the SOP's content goes:

| `delivery` | In the prompt | Fetched with the `get_sop` tool |
|---|---|---|
| `prompt` | everything | nothing |
| `auto` | name, scope, forbidden actions, warning signs | goal, guidance, steps |
| `tool` | name, scope | everything else |

Use `prompt` unless the agent is set up with a `get_sop` tool. Forbidden actions and warning signs stay in the prompt under `auto` because they must apply even if the agent never fetches the SOP.

## agents/\<id\>.yaml

```yaml
livekit: tonys-pizza                 # exactly one of livekit | vapi | elevenlabs
inherits: [pizza-context]
exclude: [delivery-handling]
variables:
  restaurant_name: Tony's Pizza
instructions: |
  Tony's is a wood-fired pizza shop in Brooklyn. Pickup only after 10pm.
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `livekit` | string | — | LiveKit `agent_name`. |
| `vapi` | string | — | Vapi assistant id. |
| `elevenlabs` | string | — | ElevenLabs `agent_id`. |
| `inherits` | list of base ids | `[]` | Bases to include, in order. |
| `exclude` | list of ids | `[]` | Bases or SOPs that target this agent but shouldn't apply. Locked ones can't be excluded. |
| `variables` | map | `{}` | Values for `{{placeholders}}`. Override `sopc.yaml` defaults. |
| `instructions` | string | `""` | Text only this agent gets. |

Set exactly one platform field. Elsewhere in sopc, refer to the agent by its id (the file name) or by its platform ref, e.g. `livekit:tonys-pizza` or `vapi:asst_9f3e`.

## Placeholders

`{{name}}` works in any text: base bodies, agent `instructions`, and every SOP field. Names use letters, digits, `_`, `-` and `.`. Each agent must have a value for every placeholder in the blocks it uses.

## Recipes

| You want | Do this |
|---|---|
| Text every agent gets | A base with `agents: "*"`. Add `locked: true` if no agent may opt out. |
| Text a group of agents gets | A base the group's agents list in `inherits`, or a base with `agents: [a, b, c]`. |
| A family of agents with shared context | A chain: `pizza-context` inherits `restaurant-host`; pizza agents inherit `pizza-context`. |
| Text one agent gets | That agent's `instructions`. |
| The same sentence with a different value per agent | A placeholder in the shared block, with each agent's value in `variables`. |
| One agent skips a shared SOP | Add the SOP id to that agent's `exclude`. |
| One agent needs a different version of a locked block (e.g. a Spanish brand voice) | In the locked block, `exclude: [that-agent]`. Add a second block with `agents: [that-agent]`, locked too. Agents can't exclude locked blocks themselves; the exception lives in the block. |
| Something said at the end of every call | A base with `agents: "*"` and `position: bottom`. |
| A procedure only some agents follow | An SOP with `agents: [ids]`. |

## Converting an existing prompt

1. Split the prompt into: identity and voice (bases), procedures (SOPs), and facts about this one agent (`instructions`).
2. Write each procedure as a Markdown SOP: the goal as `**Goal:**` and the trigger as `**When:**`. Turn numbered instructions into `## Steps`, "never"/"don't" lines into `## Never`, and "if the caller…, transfer/escalate" lines into `## Warning signs`. Put the rest in paragraphs under the name (guidance).
3. Text that appears in several prompts belongs in one base or SOP, not copied into each agent.
4. Replace per-agent values inside shared text (names, links, phone numbers) with placeholders.
5. Run `sopc fmt`, then `sopc`, and compare the output to the original prompt.

## Formatting and converting

`sopc fmt` rewrites Markdown SOP files in one canonical style: sections in the standard order, numbered steps, `-` bullets, one blank line between blocks, markers as `` `tool: name` `` then `` `required` ``. Front matter is kept as written. Add `--yaml` to format YAML SOP files too: keys in a fixed order (`name`, the settings, `description`, `scope`, `guidance`, then the step lists), default settings left out, multi-line text as `|` blocks. `sopc fmt --check` writes nothing, lists the files that would change and exits 1 if there are any (for CI).

`sopc convert --to md` (or `--to yaml`) rewrites SOPs in the other format: all of them, or the ids given (`sopc convert --to md allergen-check`). It writes the new file and deletes the old one. Comments at the top of a YAML file become front-matter comments, and back.

**Nothing destructive happens without `-y` / `--yes`.** Some rewrites can't keep every comment: a YAML file's comments below the top block, or trailing comments on front-matter settings when converting to YAML. Both commands leave such a file as it is, list it with the exact comments it would lose, and exit 1. Edit it by hand, or rerun with `--yes` to remove those comments:

```
procedures/takeout.yaml: not formatted: it would remove 2 comment(s); edit it by hand, or rerun with --yes to remove them
  line 2: # the heading agents see
  line 6: # ask first
```

Neither command changes any agent's prompt or `get_sop` payload; each checks this and refuses a file it can't rewrite exactly (`convert_failed`), e.g. a YAML `description` with line breaks, which a Markdown field can't keep. Converting may change SOP hashes in `build/lock.json` when only whitespace differs (e.g. the trailing newline of a `|` block).

## Validation

`sopc validate` reports these; every error names the file, and Markdown errors give the line number (`procedures/x.md: error [md_unknown_section] line 14: ...`). `sopc fmt` and `sopc convert` also report `convert_failed` (see above).

| Code | Severity | Meaning |
|---|---|---|
| `missing_config` | error | No `sopc.yaml` in the folder. |
| `invalid_yaml` | error | A file isn't valid YAML (including a key written twice), or isn't a mapping. |
| `colon_in_step` | error | A step contains `: ` and YAML read it as a key and value. Put the whole step in quotes. |
| `unquoted_value` | error | A step YAML read as a number or boolean (`- 10`, `- true`). Put it in quotes. |
| `empty_step` | error | A list item with nothing after the `-` (or only markers, in Markdown). |
| `invalid_field` | error | Unknown field, wrong type, missing `name`, or not exactly one platform. |
| `missing_steps` | error | An SOP has no steps: YAML `procedureSteps` missing or empty, or Markdown without `## Steps` or with no items under it. |
| `duplicate_file` | error | An SOP exists as both `<id>.md` and `<id>.yaml`. Keep one. |
| `md_settings_field` | error | A Markdown SOP's front matter sets something other than `id`, `agents`, `exclude`, `locked`, `delivery` (e.g. `name`); write it in the body. |
| `md_missing_name` | error | No `# <name>` heading. |
| `md_extra_name` | error | A second `# ` heading. |
| `md_text_before_name` | error | Text before the `# <name>` heading. |
| `md_heading_level` | error | A `###` (or deeper) heading. |
| `md_unknown_section` | error | A `##` heading other than `Steps`, `Never`, `Warning signs`. |
| `md_duplicate_section` | error | The same `##` section twice. |
| `md_unknown_field` | error | A bold label other than `**Goal:**` or `**When:**`, e.g. `**Objective:**`. |
| `md_duplicate_field` | error | `**Goal:**` or `**When:**` given twice. |
| `md_text_in_section` | error | Text under a `##` section that isn't a list item or an indented continuation. |
| `md_bad_annotation` | error | A malformed tool marker: `` `tool:` `` without a name, `` `tools: x` ``, `` `tool: two words` ``, or two tool markers. |
| `md_required_outside_steps` | error | `` `required` `` under `## Never` or `## Warning signs`. |
| `md_empty_section` | warning | `## Never` or `## Warning signs` with no items. |
| `id_mismatch` | error | An explicit `id:` differs from the file name. Usually just remove `id:`. |
| `duplicate_id` | error | A base and an SOP share an id. |
| `duplicate_platform_ref` | error | Two agents point at the same platform agent. |
| `unknown_agent` | error | `agents` or `exclude` names an agent that doesn't exist. |
| `unknown_base` | error | `inherits` names a base that doesn't exist. |
| `unknown_block` | error | An agent's `exclude` names a block that doesn't exist. |
| `unknown_sop` | error | `sop_order` names an SOP that doesn't exist. |
| `inheritance_cycle` | error | Bases inherit each other in a loop. |
| `locked` | error | An agent excludes a locked block. |
| `unset_variable` | error | A placeholder has no value for some agent. |
| `missing_goal` | warning | An SOP has no goal (`**Goal:**` or `description`). |
| `useless_exclude` | warning | An agent excludes a block that doesn't target it anyway. |

## Checklist for coding agents

1. Find the sopc root: the folder containing `sopc.yaml`.
2. Before adding text to an agent, check whether a base or SOP already covers it. Prefer editing the shared block over copying text into agents.
3. Change only files in `bases/`, `procedures/`, `agents/` and `sopc.yaml`. Never edit `build/`.
4. Run `sopc validate` and fix every error. Commands use `sops/` (or the current folder) by default; if the root is elsewhere, pass it to each one, e.g. `sopc validate path/to/root`.
5. Run `sopc plan` (it compares with the default branch; `--against REF` to choose) and confirm that only the agents you meant to change appear.
6. Run `sopc check`. If your change introduced a duplicate or conflict, fix it; report pre-existing ones to the user.
7. Run `sopc fmt`, then `sopc` so `build/` matches.
8. Never pass `--yes` to `sopc fmt` or `sopc convert` on your own. If one of them lists a file it won't rewrite because comments would be lost, tell the user and let them decide.

To convert existing prompts into this format, follow the `sopc-import` skill (`sopc skills install`).
